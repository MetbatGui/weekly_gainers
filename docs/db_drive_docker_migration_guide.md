# DB SSOT + Google Drive 동기화 + Docker 전환 가이드

이 문서는 `weekly_gainers`를 "Google Drive 매니페스트(JSON)+Excel 왕복 파싱이 SSOT"에서
"SQLite DB가 SSOT" 구조로, 그리고 로컬 배치 실행에서 Docker 컨테이너 내장 cron 실행으로
전환하면서 겪은 문제와 그 해결 이유를 정리한 것입니다. `new_stock_crawler`의 동일 계열
마이그레이션 가이드를 참고해 같은 형식으로 작성했습니다. 다른 크론잡을 같은 형태(DB SSOT +
Docker)로 옮길 때 이 문서의 체크리스트를 먼저 훑고 시작하세요.

---

## 1. 배경 — 왜 바꿨는가

기존 구조(`GoogleDriveReportStorageAdapter`)는 연도별 JSON 매니페스트에 이벤트 메타데이터를
쓰고, 종목 데이터는 업로드된 Excel 파일 자체를 SSOT로 삼았습니다. `get_by_id()`를 호출할
때마다 Excel을 다시 다운로드해 `pandas.read_excel`로 파싱하고, 콤마 제거·zfill 등으로 도메인
객체를 역복원했습니다. 문제는:

- **왕복 파싱이 느리고 취약함** — Excel 서식이 바뀌면 조용히 깨질 수 있는 구조.
- **조회할 때마다 네트워크 I/O** — 로컬 조건부 조회(예: 특정 연도만)가 불가능.
- **크론이 며칠 못 돌면 그 구간이 영영 누락** — 매일 "지난 기간 확정 + 이번 기간 갱신"만
  수행했고, 갭을 감지해 따라잡는 메커니즘이 없었음.

그래서 **SQLite(연도별 분리 파일 `db/{weekly,monthly}/{year}.db`)를 SSOT로 두고, Excel은
순수 산출물로만 남기며, DB 이벤트와 달력으로 기대 기간을 매번 계산해 누락·불완전 기간을
자동 복구하는 방식**으로 바꿨습니다. 별도의 `last_sync_date`나 메타 DB는 사용하지 않습니다.

## 2. 실제로 발생했던 문제와 원인

### 2.1 오케스트레이션 로직이 서비스 내부에 뒤섞여 있었음

`WeeklyGainerService`에 WEEKLY/MONTHLY 분기가 거의 동일하게 중복된 `sync_pipeline()`이
붙어 있었습니다. `new_stock_crawler`의 `CrawlOrchestratorService` 패턴을 따라
`CollectionOrchestratorService`로 호출 순서 조합만 분리했습니다.

리팩터링 중 코드 리뷰에서 오케스트레이터가 `self.service.repo`/`self.service.gdrive`처럼
서비스 내부 속성에 직접 접근하는 캡슐화 위반을 지적받았습니다 — `WeeklyGainerService`의
속성명이 나중에 바뀌면 오케스트레이터가 조용히 깨지는 구조였습니다. `sync_manifest()`/
`sync_db_to_drive()`를 서비스의 공개 메서드로 만들어 오케스트레이터는 서비스의 공개
인터페이스만 호출하도록 수정했습니다.

**교훈:** 오케스트레이터를 분리할 때 "내부 상태에 접근하는 것"과 "공개 메서드를 호출하는
것"을 처음부터 구분할 것. 리뷰에서 걸러지긴 했지만, 설계 단계에서 바로 공개 메서드로
시작하면 이 왕복을 줄일 수 있음.

### 2.2 연도/월 경계에서 방금 FINAL 확정한 데이터가 동기화 누락

`run_daily_sync()`가 매니페스트/DB Drive 동기화를 `current_year`(또는
`current_month_year`) 기준으로만 수행했습니다. 1월 초처럼 `prev_year != current_year`인
날에는, 그 직전 호출에서 방금 FINAL 확정한 지난해 마지막 주(또는 12월) 데이터가 어느
동기화 대상에도 포함되지 않고 영영 Drive에 안 올라가는 버그였습니다. `prev_year`가
`current_year`와 다르면 그 연도도 별도로 동기화하도록 수정.

**교훈:** "표준 처리 범위"(지난 기간+이번 기간)와 "동기화 대상 범위"를 별개로 계산하면,
경계 케이스(연도/월 전환일)에서 둘이 어긋나기 쉽다. 코드 리뷰에서 "오늘 날짜를 경계로
주입해서 유닛테스트"(`today` 파라미터 주입)로 실제로 잡아냈다 — 이런 경계 로직은 시간
주입 없이는 발견하기 어려움.

### 2.3 진행 중인 이번 달을 갭으로 오인해 조기 FINAL 확정

갭 백필 로직(`compute_gap_months`)이 `last_sync_date`와 오늘 사이 공백이 임계값(7일)을
넘으면 그 사이 기간을 모두 "누락"으로 간주했는데, `last_sync_date`가 **이번 달 안에** 있는
경우(예: 6/1에 마지막 동기화 후 6/26에 재개, 공백 24일 > 7일)에도 이번 달 자체를 갭으로
포함시켜 `is_final=True`로 조기 확정해버리는 버그가 있었습니다. `collect_period`는 이미
FINAL인 이벤트를 `force` 없이는 재수집하지 않으므로, 한 번 이렇게 잘못 확정되면 그 달의
나머지 실시간 업데이트와 월말 정식 확정이 전부 스킵되는 영구 손상이었습니다.

원인은 갭 계산이 "표준 지난 기간"만 경계로 알고 "표준 이번 기간"은 경계로 취급하지
않았던 것. `prev_period`와 `current_period`를 둘 다 명시적으로 전달받아 항상 갭에서
제외하도록 수정.

**교훈:** "이 기간은 이미 표준 흐름이 처리하니 갭 계산에서 빼야 한다"는 경계가 두 개
(지난 기간, 이번 기간) 있다면 둘 다 명시적으로 넘길 것. 하나만 챙기면 나머지 하나가
경계값 근처에서 조용히 새어 들어간다.

### 2.4 수집 실패에도 last_sync_date가 전진 — 갭 백필이 무력화됨

`run_daily_sync()`가 `collect_week`/`collect_month`의 성공 여부와 무관하게 매 실행 끝에
`set_last_sync_date(today)`를 호출했습니다. KRX API가 며칠간 응답하지 않아
`collect_period`가 매번 `False`를 반환해도 `last_sync_date`는 계속 "오늘"로 갱신되므로,
다음 성공한 실행에서 `last_sync_date`와 오늘 사이 공백이 작게 보여 정작 실패했던 기간이
갭 백필 대상에서 빠지는 문제였습니다. 이번 실행의 모든 collect 호출이 성공했을 때만
`last_sync_date`를 전진시키도록 수정.

**교훈:** "언제 실행했는가"와 "언제 실제로 성공했는가"를 같은 값으로 기록하면 안 된다.
재시도/백필 메커니즘의 기준일은 반드시 성공 시점만 기록해야 갭 감지가 의미를 가진다.

### 2.5 SQLite 스키마 DDL이 읽기 경로에서도 매번 재실행됨

`SqliteReportStorageAdapter._connect()`가 `save()`/`get_by_id()`/`exists()` 모든 경로에서
`CREATE TABLE IF NOT EXISTS`를 두 번씩 실행했습니다. 읽기는 파일 존재 여부를 먼저
확인하고 나서 연결하므로(존재하면 스키마도 이미 있음이 보장됨) 불필요한 DDL이었습니다.
쓰기 전용 `_connect_and_init()`과 읽기 전용 `_connect_readonly()`로 분리. 같은 리뷰에서
`items` 테이블에 `event_id` 인덱스가 없어 `DELETE`/`SELECT`가 풀스캔되는 것도 함께 발견해
인덱스를 추가했습니다.

**교훈:** "매번 안전하게 스키마를 보장"하는 습관이 읽기 경로까지 무의식적으로 퍼지기
쉽다. 쓰기와 읽기의 연결 책임을 처음부터 나누면 이런 낭비가 리뷰 전에도 잘 안 보인다 —
작게 시작한 헬퍼 하나(`_connect`)에 책임이 계속 얹히는 패턴을 경계할 것.

### 2.6 1회성 스크립트에 영구 테스트를 붙였다가 되돌림

이관 스크립트(`scripts/migrate_manifest_to_sqlite.py`)를 만들면서 Walking Skeleton 습관대로
유닛테스트(`tests/unit/test_migrate_manifest_to_sqlite.py`)와 이를 위한
`pyproject.toml`의 `pythonpath` 추가까지 같이 커밋하려 했으나, "스크립트에 테스트가 있으면
안 된다"는 피드백을 받고 되돌렸습니다. `new_stock_crawler`의 동일 스크립트
(`scripts/migrate_parquet_to_sqlite.py`)도 테스트 없이 실제 데이터 1회 실행 + 건수 비교로만
검증했던 것과 같은 결이었습니다. 이관이 실제로 끝나고 검증된 뒤(WEEKLY 82건, MONTHLY 8건
전량 이관 확인)에는 스크립트 자체도 컷오버 커밋에서 삭제했습니다.

**교훈:** `scripts/`·`scratch/` 아래 코드는 처음부터 "언젠가 지울 것"으로 취급할 것. 정식
프로덕션 코드(어댑터/서비스)에는 TDD를 그대로 적용하되, 그걸 호출만 하는 1회성 스크립트
래퍼 자체에는 영구 테스트를 붙이지 않는다. 실행 후 남겨두지 말고, 검증이 끝나면 삭제한다.

### 2.7 Docker: ENV TZ가 cron 잡에 반영되지 않음

`Dockerfile`에 `ENV TZ=Asia/Seoul`만 설정했는데, 실제로 컨테이너를 빌드해 `date` 명령을
찍어보기 전까지는 문제가 안 보였습니다. cron이 스폰하는 잡 프로세스는 Dockerfile의 `ENV`를
상속받지 않습니다 — `new_stock_crawler` 가이드가 `PATH`/`PLAYWRIGHT_BROWSERS_PATH`에서 이미
겪은 것과 완전히 같은 부류의 문제였는데도, TZ에는 같은 체크리스트를 처음에 적용하지
않았습니다. `RUN ln -snf /usr/share/zoneinfo/$TZ /etc/localtime`으로 타임존을 이미지
빌드 시점에 OS 레벨(`/etc/localtime`)에 직접 구워서 해결 — `TZ` 환경변수를 아예 unset한
채로 `date`를 실행해도 KST가 나오는 것으로 검증했습니다. 이 방식은 cron의 환경변수
상속 여부와 완전히 무관하게 동작합니다.

같은 리뷰에서 `apt-get install cron tzdata`가 `COPY . /app` 이후에 있어서 앱 소스가
바뀔 때마다 이 레이어가 불필요하게 재실행되던 것도 발견해 `COPY` 이전으로 옮겼습니다.

**교훈:** "Dockerfile의 ENV는 cron 잡에 상속되지 않는다"는 교훈을 이미 문서로 알고
있어도, 새로 추가하는 환경변수 하나하나에 그 체크리스트를 다시 적용해야 한다 — 알고
있다는 것과 모든 신규 항목에 실제로 적용하는 것은 다르다. 의심스러우면 그 값에 의존하는
로직을 env 상속 없이(`unset` 후) 직접 실행해서 확인할 것.

### 2.8 .env를 bind mount에서 env_file로 바꾸면 오히려 회귀

Docker 리뷰에서 "`.env`가 로컬에 없으면 Docker가 그 경로에 빈 디렉토리를 대신 마운트해
로드가 조용히 실패한다"는 지적을 받고, 처음엔 `docker-compose.yml`의 `.env` 파일 bind
mount를 `env_file:` 지시자로 바꾸려 했습니다. 하지만 `env_file`은 컨테이너의 **PID 1
프로세스**에만 OS 환경변수를 주입하고, cron이 스폰하는 잡은 그 환경변수도 상속받지
못합니다(2.7절과 같은 이유). 반면 현재 방식(파일 bind mount)은 `main.py`의
`load_dotenv()`가 매 실행마다 그 파일을 직접 다시 읽으므로, cron 잡 프로세스 안에서도
항상 정상 로드됩니다. `env_file`로 바꾸는 건 "고치는 것"이 아니라 cron 경로에 새로운
회귀를 만드는 것이었습니다 — 파일 mount 방식을 유지하고, 대신 `.env`가 로컬에 반드시
있어야 한다는 전제만 주석으로 명시했습니다.

**교훈:** 리뷰 지적을 그대로 받아들이기 전에 "이 수정이 cron처럼 환경을 다시 구성하는
경로에도 똑같이 적용되는가"를 먼저 확인할 것. 같은 문제(env 미상속)를 이미 한 번 겪은
프로젝트라면, 겉보기에 더 "표준적인" 대안(`env_file`)이 오히려 그 문제를 재도입할 수
있다.

### 2.9 "변화 없음" 판정보다 비싼 외부 조회가 먼저 실행되고 있었음

`collect_period()`가 매번 (1) 종목 데이터 수집 → (2) KOSPI_200/KOSDAQ_150 구성종목 조회
(시작일+종료일 × 2지수 = 외부 API 4회, 캐시 미스 시 네트워크 왕복) → (3) fingerprint
비교 → 변화 없으면 스킵, 순서로 짜여 있었습니다. 그런데 fingerprint는 (2)의 결과와
무관하게 (1)의 결과만으로 계산 가능했고, (2)는 오직 "변화가 있을 때"만 필요한
리포트용 필터 구성에 쓰였습니다. 즉 휴장일이나 데이터 미변경 상황에서도 매 실행마다
불필요한 외부 조회 4회를 먼저 치른 뒤에야 "건너뜁니다"를 출력하고 있었습니다.
(2)와 (3)의 순서를 바꿔, fingerprint가 기존과 같으면 (2)를 아예 실행하지 않고 조기
종료하도록 수정. 실패 재현 통합 테스트(`fetch_index_components` 호출 횟수를 0으로
검증)를 먼저 작성해 버그를 고정한 뒤 고쳤습니다.

**교훈:** "이번 실행에서 할 일이 있는가"를 값싸게 판정할 수 있는 조건(로컬 계산만으로
가능한 fingerprint 등)이 있다면, 그 판정을 비싼 외부 호출(네트워크 API, DB 원격 쓰기
등)보다 먼저 배치할 것. 저장 직전에야 "변화 없음"을 알게 되는 구조는 매 실행마다
쓸데없는 비용을 반복해서 낸다 — 순서를 정할 때 "이 단계의 결과가 다음 판정에
쓰이는가, 판정 이후에만 쓰이는가"를 먼저 따질 것.

### 2.10 휴장일은 수집하지 않는다

이 배치는 거래소 휴장일에는 KRX 데이터를 수집하거나 DB 완전성 검사를 실행하지 않고
정상 종료한다. 휴장일에 생긴 미확정 기간과 누락 복구는 **다음 거래일 실행**에서 DB의
이벤트와 달력을 다시 대조하여 처리한다. 따라서 휴장일 스킵은 데이터 완전성 판단을 위한
별도 상태값을 만들거나 `last_sync_date`를 갱신하는 근거가 되어서는 안 된다.

**교훈:** 휴장일의 "수집하지 않음"은 의도된 운영 정책이다. 다만 다음 거래일의 DB 감사가
휴장일을 포함한 과거 누락을 발견·복구하는지 경계 테스트로 보장해야 한다.

## 3. 다른 크론잡을 같은 구조로 옮길 때 체크리스트

1. **왕복 파싱 대신 타입 그대로 저장**: 산출물(Excel 등)을 SSOT로 재파싱하지 말고, SQLite에
   도메인 타입 그대로 저장해 조회 시 파싱을 없앨 것.
2. **오케스트레이터는 서비스의 공개 메서드만 호출**: 내부 속성(`self.service.repo`,
   `self.service.gdrive` 등)에 직접 접근하지 말고, 서비스에 위임용 공개 메서드를 만들 것.
3. **"표준 처리 범위"와 "동기화/백필 대상 범위"를 같은 값으로 명시적으로 공유**: 재계산하지
   말고 파라미터로 넘겨서, 경계일(연/월 전환)에 둘이 어긋나지 않게 할 것.
4. **갭 계산은 지난 기간과 이번 기간을 둘 다 경계로 제외**: 하나만 챙기면 진행 중인
   현재 기간이 갭으로 오인되어 조기 확정될 수 있음.
5. **"성공 시점"과 "실행 시점"을 구분해서 기록**: 재시도/백필 기준일은 반드시 성공했을
   때만 전진시킬 것. 실패해도 전진시키면 그 실패 구간이 다시는 안 잡힌다.
6. **쓰기 전용 연결과 읽기 전용 연결을 분리**: 스키마 보장(DDL)은 쓰기 경로에서만, 읽기는
   파일 존재 확인 후 스키마가 있다고 신뢰하고 연결할 것. 자주 조회되는 FK 컬럼에는 인덱스.
7. **`scripts/`의 1회성 코드에는 영구 테스트를 붙이지 말 것**: 프로덕션 어댑터/서비스는
   TDD, 이를 호출만 하는 스크립트 래퍼는 실행+수치 검증으로 충분. 검증 끝나면 삭제.
8. **Dockerfile의 `ENV`는 cron 잡에 상속되지 않는다는 걸 신규 변수마다 다시 적용**: 특히
   `TZ`처럼 "당연히 되겠지" 싶은 값일수록 실제로 `unset` 후 검증할 것 —
   타임존은 `/etc/localtime` 심볼릭 링크로 OS 레벨에 굽는 게 env 상속 여부와 무관해서 더
   안전함.
9. **cron 잡에 값을 전달하는 "더 표준적인" 대안(`env_file` 등)을 도입하기 전에, 그 대안도
   cron 잡 프로세스까지 실제로 전달되는지 확인**: 파일을 직접 읽는 방식이 의도적으로 env
   미상속 문제를 피하고 있었다면, 표준적으로 보이는 대안이 오히려 회귀일 수 있다.
10. **apt-get 설치 레이어는 `COPY . /app`보다 앞에**: 앱 소스 변경이 OS 패키지 레이어의
    캐시를 깨지 않도록.
11. **실제 이미지를 빌드/기동해서 검증**: `docker build` → `docker compose up`으로
    cron이 PID 1로 뜨는지, `/etc/cron.d/*` 권한(0644)이 맞는지, 볼륨(`db/`, `secrets/`)이
    실제 마운트되는지, `.env`가 실제로 로드되는지 확인할 것.
12. **"변화 없음" 판정을 비싼 외부 조회보다 먼저 배치**: fingerprint/해시처럼 로컬
    계산만으로 가능한 조기 종료 조건이 있다면, 그 판정을 네트워크 API 호출이나 원격
    쓰기보다 먼저 실행해서 불필요한 실행마다 그 비용을 반복하지 않도록 할 것.
13. **`.gitattributes`로 셸 스크립트 줄바꿈 강제**: `docker/*.sh`, `Dockerfile` 등
    리눅스 컨테이너에 그대로 복사되는 파일은 `text eol=lf`로 고정. Windows에서 작업하는
    경우 특히 중요 — 로컬 빌드가 잘 되는 것과 재체크아웃 후에도 깨지지 않는 것은 별개.
14. **cron 데몬 기동에 root가 필요해도, 실제 페이로드는 `su`/`gosu`로 nonroot로 낮출
    것**: root는 cron 데몬 기동과 `/proc/1/fd/1` 리다이렉션에만 필요함 (fd는 `open()`
    시점에만 권한 체크되므로, root가 먼저 열어둔 리다이렉션은 nonroot 자식 프로세스도
    그대로 상속받아 로그가 정상적으로 써짐).
15. **cron 잡 스크립트는 PATH에 의존하지 말고 절대경로로 실행**: Dockerfile의
    `ENV PATH`는 cron이 스폰하는 잡 프로세스에 상속되지 않음.
16. **자주 쓰는 도커 명령어는 `justfile`/`Makefile`로 정리**: `build`/`up`/`deploy`처럼
    반복되는 조합을 한 줄 명령으로 묶어두면, 재기동을 깜빡하고 낡은 이미지로 배포 상태를
    남겨두는 실수(코드 머지 후 컨테이너 재기동 누락)를 줄일 수 있음.
17. **휴장일에는 수집과 DB 감사를 모두 실행하지 않음**: 다음 거래일 실행이 DB 이벤트와
    달력을 대조해 해당 공백을 복구해야 하며, 휴장일 스킵을 기록하는 별도 동기화 상태값은
    두지 말 것.

## 4. 아직 다루지 않은 것 (의도적으로 미룬 항목)

- **Google Drive 동시 쓰기에 대한 파일 락**: 지금은 cron 하나만 순차 실행이라 불필요,
  병렬 실행 잡이 생기면 재검토.
- **DB 파일 자체의 Drive 업로드 변경분 감지**: 지금은 매 sync마다 무조건 업로드(파일이
  작아 비용 무시 가능한 단순화). 파일이 커지면 지문 비교 기반으로 바꿀 것.
- **크론 실행 결과 알림**: healthchecks.io류 cron 모니터링 서비스에 ping을 붙이는 방식을
  권장하되 아직 미착수.
- **`scripts/force_recollect_*.py` 등 `scratch/`에 남아있는 구 어댑터 참조 스크립트 정리**:
  gitignore 대상이라 당장 CI/배포에는 영향 없음. 필요 없어지면 삭제할 것.
- **`print()` 미교체 상태로 Docker 전환**: `src/` 전체에 `print()`가 51곳 남아있음.
  `new_stock_crawler`가 이미 겪은 위험(비-TTY 환경에서 `print()`의 버퍼링과 `logging`의
  flush 타이밍이 어긋나 로그 순서가 실제 실행 순서와 다르게 보일 수 있음 — "중복 실행"으로
  오인하기 쉬움)이 이 프로젝트에도 그대로 적용됨. 아직 실제 로그 순서 뒤섞임을 관찰하진
  못했지만, 문제가 재현되면 `logging`으로 전량 교체할 것.
